It covers frontend, backend, APIs, data model, security, realtime, deployment, and every core function with inputs, outputs, side effects, and errors.

Tech stack (recommended)

Backend: Python, FastAPI.

Fast. Async capable. Easy WebSocket support.

DB: SQLite for prototype.

Simple, file-based, easy to commit to repo. Use SQLAlchemy.

Worker/Queue: DB-backed FIFO (simple) or in-memory circular queue for single-server.

Hashing: hashlib (SHA256) for Merkle, bcrypt for PIN hashing.

Realtime: WebSocket (FastAPI with websockets or Socket.IO).

Frontend: React (single page). Use plain CSS or Tailwind.

Deployment: Frontend to GitHub Pages. Backend to any free/cheap host (Render, Fly, Vercel serverless, or a VPS). Use HTTPS.

High-level architecture

Browser clients (React) connect to server via REST and WebSocket.

Server holds accounts, ledger, Merkle module, queue.

Client sends transfer/login requests to REST.

Server validates, enqueues transaction record (status = pending).

Worker processes the queue sequentially.

Worker appends to ledger, rebuilds Merkle root, stores snapshot, broadcasts update over WebSocket.

Clients display the ledger and balances in real time.

Queue strategy (web-safe)
Option A (recommended for reliability)

DB-backed queue: Transaction rows with status = pending.

Processing worker: SELECT pending ORDER BY timestamp FOR UPDATE. Mark processing, commit, then apply.
Benefits: survives server restart. No external Redis required.

Option B (simpler)

In-memory circular queue class used when server single-process.

Must persist ledger to DB quickly to avoid loss.

Merkle module — functions and details
Module name: merkle.py

tx_to_string(tx: Transaction) -> str

Inputs: transaction object or dict.

Output: canonical string.

Side effect: none.

Note: order fields: id|timestamp|sender|receiver|amount|meta.

hash_data(data: str) -> str

Input: string.

Output: hex SHA256 string.

build_merkle_tree(tx_hashes: List[str]) -> (root: str, tree: List[List[str]])

Input: list of leaf hashes in ledger order.

Output: root hash and optional tree structure (levels).

Behavior: if odd count, duplicate last hash. Pairwise concat then hash.

get_merkle_proof(tx_index: int, tree: List[List[str]]) -> List[(sibling_hash, is_left)]

Input: index of tx in leaves.

Output: merkle proof path.

verify_proof(leaf_hash: str, proof: List, root: str) -> bool

Ledger module — functions and details
Module name: ledger.py

append_transaction(tx: Transaction) -> ledger_index

Input: transaction object (must have tx_hash).

Output: assigned ledger_index (int).

Side effects: insert Transaction with status processed, set ledger_index, update Balance for accounts (inside DB txn), return index.

remove_transaction(ledger_index: int, reason: str) -> bool

Input: index.

Output: success flag.

Side effects: mark tx as rolled_back, revert balances using inverse operation or restore from snapshot. Use rollback mechanism described below.

get_transactions(offset=0, limit=100) -> List[Transaction]

Input: paging.

Output: transactions ordered by ledger_index.

build_and_store_merkle() -> root

Input: none. Uses processed transactions in order.

Output: new root string.

Side effects: create a LedgerSnapshot row with root and last_tx_index. Optionally store tree.

snapshot_state() -> snapshot_id

Input: none.

Output: snapshot id.

Side effects: store accounts balances and transaction index in snapshot. For SQLite, export JSON of accounts and last_tx_index, or copy DB file.

Rollback strategy (detailed)
Two safe strategies. Choose one.

Strategy 1, preferred for simplicity and correctness:

After every processed transaction commit, create a snapshot row recording: last_tx_index, merkle_root, accounts balances (JSON) or a copy of DB file.

If fraud detected at tx k, find last valid snapshot with last_tx_index < k. Restore accounts balances from snapshot and delete/mark transactions with index > snapshot.last_tx_index as rolled_back. Rebuild merkle root from remaining transactions. Broadcast rollback event.

Strategy 2, inverse operation log:

For each processed tx, store inverse operation that will revert balances. On rollback, apply inverse ops in reverse order until ledger index restored. This is space efficient but more error prone.

Notes:

For prototype use snapshots every N transactions (e.g., every 1 or 5) to simplify rollback. Snapshots cost space but are clear to explain.

Fraud detection and verification functions

verify_integrity() -> (valid: bool, details)

Rebuild merkle root from DB, compare with latest snapshot/expected root.

If mismatch, perform locate_mismatch().

locate_mismatch() -> (tx_index_or_id)

Binary search approach: split ledger in halves, compute root for each half, find which half differs. Repeat to locate smallest mismatched tx. This is efficient.

API endpoints (REST) — full detail
Base path: /api/v1

Auth: Use JWT for auth. Use HTTPS.

POST /login

Body: {account_id, pin}

Success: 200 {token, account_id, balance}

Errors: 401 wrong pin, 423 locked

POST /transfer

Auth required.

Body: {to_account_id, amount}

Serverside steps:

verify token and accounts exist.

check balance.

create Transaction row status pending, tx_hash computed.

return 202 {tx_id, status: pending}.

Errors: 400 invalid amount, 402 insufficient balance.

POST /process_next (admin or worker-only)

Secured endpoint called by worker or same server internal process.

Body: none or {max_count}

Action: find oldest pending txs, process sequentially by calling append_transaction and build_and_store_merkle per tx or batch.

Return: summary {processed: n, root: current_root}

GET /transactions?offset=&limit=

Returns processed transactions.

GET /merkle/root

Returns current merkle root and last_tx_index.

POST /verify

Body optional: {root}

Returns: {valid:bool, details, mismatch_tx_id: optional}

POST /rollback

Admin only. Body: {to_snapshot_id} or {to_tx_index}

Action: restore snapshot state.

Return: {success, restored_to_index, new_root}

GET /accounts/{id}

Auth required and permitted only for the owner. Returns balance and last transactions.

WebSocket /ws

Events:

on_connect: authenticate via token.

server->client messages:

ledger_update {tx, new_root, balances_changed}

integrity_alert {details}

rollback_notice {restored_to_index, new_root}

Client receives real-time updates.

Security details (must cover in presentation)

Always use HTTPS in deployment.

Hash PIN with bcrypt before storing. Never store plaintext PIN.

Use JWT with short expiry and refresh tokens.

Rate limit login attempts. Lock account for a period after 3 failed attempts.

Validate all inputs server-side.

Use parameterized SQL queries (SQLAlchemy does this).

Log all sensitive actions in AuditLog.

Use TLS for WebSocket (wss://).

If you implement encryption over sockets, use TLS rather than custom crypto. For extra credit, show message-level encryption with Fernet for payloads.

Concurrency and consistency

Use DB transactions for balance updates and ledger append.

In SQLAlchemy use session.begin() to ensure atomic updates.

Use row-level locks or SELECT FOR UPDATE when selecting accounts to prevent race conditions.

Worker must process one tx at a time (sequential) or lock accounts involved.

Final practical tips

Keep functions small and tested.

Use DB-backed queue to avoid lost pending transactions.

Keep merkle rebuild simple: rebuild from processed transactions each commit for prototype.

Later, implement incremental merkle update if you need speed.
